# 타당성 검토

검토일: 2026-10-05. 대상: 로컬·사무실 모두 macOS, 기존 Tailscale 및 SSH 설정 사용.

## 해결할 불편

현재 포트 연결 스크립트는 입력한 포트에 대해 `ssh -N -L`을 실행합니다. 포트가 바뀔 때마다 새 터널을 관리해야 합니다. 이미지 전달 스크립트는 클립보드를 PNG로 저장하고 SCP 전송 후, 원격 파일 경로를 로컬 클립보드에 복사합니다. 이미지마다 수동 호출이 필요합니다.

Worklink의 가치는 두 동작을 **업무 중 한 번 켜두는 연결**로 묶는 데 있습니다. 화면 스트리밍이나 전체 파일 동기화까지 확장하지 않아도 불편을 줄일 수 있습니다.

## 권장 형태

로컬에는 메뉴바 앱, 원격에는 SSH 세션에서 실행되는 작은 헬퍼를 둡니다. 원격 헬퍼는 연결이 끊기면 종료하고, 다음 연결에서 다시 실행합니다. 초기에는 원격 상주 LaunchAgent가 필요하지 않습니다. 로컬 로그인 시 자동 시작은 나중에 선택 기능으로 제공합니다.

업무 모드 OFF에서는 클립보드 타이머·포트 감시·재연결을 모두 중지합니다. ON에서는 연결을 재사용하며 유휴 대기합니다. 전송은 이미지가 새로 생기거나 사용자가 직접 요청했을 때만 발생합니다.

## 왜 Go를 우선 검토하는가

| 선택 | 유리한 점 | 비용과 한계 | 판단 |
| --- | --- | --- | --- |
| Go 코어 + Swift/AppKit 메뉴바 | 네트워크·스트리밍·상태 관리 구현이 간단하고 원격 단일 바이너리 배포에 적합 | 언어 2개, 로컬 코어 자식 프로세스와 Go 런타임 메모리 | 우선 제안 |
| Rust 코어 + Swift/AppKit 메뉴바 | 메모리 제어가 세밀하고 GC 없음 | macOS 통합 작업은 여전히 필요, 개발 복잡도 증가 | Go 실측이 예산을 넘으면 비교 |
| Swift 중심 + 시스템 OpenSSH | macOS API·메뉴바·권한 처리 통합이 자연스럽고 로컬 프로세스 수를 줄이기 쉬움 | 원격 헬퍼의 macOS 의존성이 높음 | 두 Mac 전용을 유지할 경우 좋은 대안 |

Go나 Rust 자체가 저전력을 보장하지 않습니다. Rust라도 0.1초마다 외부 명령을 실행하면 비쌀 수 있고, Go도 대부분 이벤트를 기다리면 CPU 사용을 낮출 수 있습니다. 현재 Swift 실험은 클립보드 감지 방식만 확인하며 언어 간 비교 근거가 아닙니다.

첫 제품의 Go 코어는 별도 프로세스로 시작해 빌드·디버깅을 단순화합니다. Swift 앱과는 표준 입출력으로 연결합니다. 메모리 예산을 넘으면 Swift 통합 또는 Rust 대체를 실제 측정으로 결정합니다. 웹뷰를 포함하는 UI는 초기 범위에서 제외합니다.

## 클립보드는 완전한 이벤트 방식으로 가정하지 않는다

Apple의 `NSPasteboard.changeCount`는 클립보드 소유권 변경을 관찰할 수 있는 공개 API입니다. 소유권 변화가 항상 새로운 이미지를 의미하지는 않으므로, 변화 확인 후 타입·내용을 검사해야 합니다. 이 설계에서는 범용 클립보드 변경 알림을 가정하지 않고 변경 번호를 확인합니다. [Apple changeCount](https://developer.apple.com/documentation/appkit/nspasteboard/changecount)

초기 제안은 ON 상태에서 1초 간격 + 10% 타이머 tolerance입니다. 변화가 없는 동안 이미지 추출·변환·해싱을 하지 않습니다. 화면 잠금·절전에서는 중지하고, 저전력 모드에서는 2초 간격 또는 명시적 보내기 모드로 바꿉니다. 복귀 때 현재 변경 번호를 기준으로 시작해 과거 클립보드 내용을 갑자기 전송하지 않습니다.

매번 `pngpaste`나 Swift 인터프리터를 실행하는 방식은 피합니다. 이미지 변환이 필요한 순간에만 한 개의 작업을 실행하고, 이미지 바이트는 작업 완료 후 해제합니다. Apple도 불필요한 타이머 중지와 tolerance 설정을 권장합니다. [Apple 에너지 가이드](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/Timers.html)

macOS의 클립보드 접근 정책은 제품 동작의 전제 조건입니다. 앱의 접근 상태를 확인하고 거부 시 자동 읽기를 반복하지 않습니다. 명시적 붙여넣기 또는 전용 스크린샷 폴더 감시로 대체합니다. 실제 배포 앱의 서명·OS 버전별 확인이 필요합니다. [Apple accessBehavior](https://developer.apple.com/documentation/appkit/nspasteboard/accessbehavior-9k4t4)

## 개발 서버를 어떻게 발견할 것인가

| 방식 | 지연·비용 | 적용 |
| --- | --- | --- |
| 서버 실행 시 `worklink run --port 5173 -- npm run dev`로 등록 | 시작·종료 이벤트 중심, 주기적 전체 검사 없음 | 우선 구현할 명령 예시 |
| 업무 프로필에 포트 등록 | SSH 리스너 유지, 서버 시작 전에도 준비 가능 | 기존 실행 명령을 유지하는 MVP |
| `worklink port add 4387` | 수동 1회 등록 후 연결·재연결 자동 관리 | 임의 포트 지원 |
| 원격 `lsof`로 리스닝 소켓 발견 | 외부 프로세스·소켓 열거 비용, 포트가 어느 프로젝트인지 모호함 | 선택형 후속 실험 |

위 CLI는 설계안이며 아직 실행할 수 없습니다. 에이전트가 임의 포트로 서버를 실행하는 현재 흐름을 완전히 자동화하려면 마지막 방식 또는 에이전트의 서버 실행 등록이 필요합니다. **등록 기반 MVP만으로 모든 서버를 자동 발견할 수는 없습니다.**

자동 발견은 초기에는 원격에서 5초 간격, 장시간 변화가 없으면 15초 간격을 후보로 측정합니다. 본인 소유 프로세스와 설정된 프로젝트·포트 규칙에 맞는 것만 후보에 넣습니다. 승인된 규칙만 자동 연결하고, DB·디버거 등 다른 리스너를 무조건 연결하지 않습니다. macOS에서 일반 앱이 모든 프로세스의 소켓 생성 이벤트를 저비용으로 받는다고 가정하지 않습니다.

현재 Mac의 짧은 실험에서는 5초 간격 리스너 검색의 평균 CPU가 하네스·자식 합산 0.34%, 1초 간격 변경 번호 확인은 실험 프로세스 기준 0.007%였습니다. 다른 환경·프로세스 구성이고 전체 시스템 비용도 아니므로 일반화할 수 없습니다. 자동 발견 비용을 별도로 검증할 필요성은 확인했습니다. [측정 조건과 원본](measurements.md)

저지연·저전력·설정 없는 자동 발견 세 가지를 동시에 보장하기는 어렵습니다. 실행 등록을 사용하면 이 제약이 가장 작아집니다.

## SSH와 Tailscale Serve 비교

SSH는 기존 호스트 별칭·키·연결 정책을 재사용합니다. `ControlMaster`/`ControlPath`로 연결을 공유하고 `ssh -O forward/cancel`로 포트를 추가·제거할 수 있습니다. 전용 control socket을 사용하고 다른 터미널의 연결을 종료하지 않습니다. 시스템 OpenSSH 버전에서 지원 여부를 확인해야 합니다. [OpenSSH 연결 공유](https://man.openbsd.org/ssh_config), [포트 제어](https://man.openbsd.org/ssh)

SSH 포워딩은 브라우저에 `http://localhost:5173`을 유지하기 좋습니다. 콜백 URL·쿠키·개발 서버 Host 검사·WebSocket 설정이 원격 호스트 주소로 바뀌는 영향을 줄입니다. 로컬 포트 충돌, IPv4/IPv6, 앱 자체가 별도 HMR 포트를 쓰는 경우는 따로 처리해야 합니다.

Tailscale Serve는 원격의 localhost 서비스를 tailnet에 제공할 수 있어 터널 관리의 대안입니다. 다만 로컬 localhost 주소를 제공하려면 추가 연결이 필요합니다. 접근 범위는 tailnet 정책으로 관리하고 HTTPS 모드의 MagicDNS·인증서 조건도 고려합니다. Worklink 기본 경로는 SSH로 두고 Serve는 선택적 후속 모드로 검토합니다. [Tailscale Serve](https://tailscale.com/docs/reference/tailscale-cli/serve), [개발 서버 공유](https://tailscale.com/docs/use-cases/application-testing/share-local-dev-server-with-team)

## 자원 목표와 판단 기준

다음 수치는 구현을 평가하기 위한 **초기 목표**이며, 앱의 실측 성능이나 보장치가 아닙니다. 각 Mac에서 Worklink와 SSH·헬퍼 자식 프로세스를 합산하고, 기존 Tailscale 비용은 동일 조건의 기준 측정에 포함합니다.

| 항목 | 초기 목표 | 검증 |
| --- | --- | --- |
| 업무 OFF | 정기 클립보드·포트 확인 0회 | Instruments·프로세스 추적 |
| 연결 ON, 변화 없음 | 평균 CPU < 0.5% / 한 코어, 각 Mac 기준 | 30분 유휴 측정 |
| 유휴 메모리 | 로컬 프로세스 합계 RSS < 80 MiB, 원격 < 40 MiB | 실제 프로세스 트리 샘플링 |
| 이미지 순간 메모리 | 각 Mac 합계 RSS < 200 MiB, 처리 후 유휴 수준 복귀 | 4K 이미지 100회 반복 |
| 클립보드 감지 | 보통 1초 + tolerance/스케줄링 지연 | 감지 구간과 전송 구간 분리 |
| 이미지 전체 전달 | 직접 연결·5 MiB 이하 이미지에서 p95 < 3초 | LAN·외부망·DERP 각각 측정 |
| 재연결 실패 | 1→2→4→8→16→30→60초, jitter, 인증 오류 시 정지 | 연결 단절·절전 시험 |
| 에너지 | 동일 작업의 기존 스크립트 대비 증가 폭 기록 후 허용 예산 확정 | Activity Monitor·Instruments, 배터리 A/B |

RSS 합산은 공유 페이지 중복을 포함할 수 있으므로 실제 메모리 부담은 physical footprint도 함께 확인합니다. CPU 비율이 작아도 주기적 wakeup·네트워크 활동이 배터리에 영향을 줄 수 있습니다. 짧은 클립보드 실험으로 전력 소비량이나 배터리 감소율을 추정하지 않습니다.

## 남은 불확실성

- 배포 앱의 클립보드 권한·App Nap·절전 복귀 동작.
- Go + Swift + SSH 전체 메모리와 이미지 변환 순간 비용.
- 기존 SSH 서버의 multiplexing/forwarding 허용 여부와 끊김 복구.
- 원격 `lsof` 자동 발견의 비용·정확도와 포트의 프로젝트 식별.
- 브라우저 HMR·OAuth·IPv6, Tailscale 직접 연결과 relay 환경 차이.
- 에이전트별 이미지 경로 입력 경험. 파일 도착과 에이전트의 이미지 해석은 별도로 검증.

권장 방향은 등록된 포트 + 이미지 전송부터 작게 만들고, 자동 발견과 UI 확장은 실제 업무에서 비용과 필요성이 확인된 다음 추가하는 것입니다.
